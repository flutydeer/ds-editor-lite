# 写更新日志（release notes）

为最终用户撰写本项目的更新日志。核心教训来自开发组实践：**AI 只读
PR 和 diff 容易"过度路径化"——把实现过程当成用户感知内容写进去**。
用户的体感是"新增了一个能正常使用的固化工具"，不是"口型当初漏了
后来补修了一版"。日志必须从**用户可感知的 bug 或需求**出发，不带
内部实现故事。

## 硬性规则

1. **只写用户可感知、能看懂的**。内部/引擎/基础设施改动（synthrt/dspx
   升级、重构、dll 名、模块名、测试、文档提交）一律不写；拿不准就略。
2. **从用户出发而不是从 diff 出发**。每个改动问"用户会看到什么/从此
   能做什么？"具体 bug 修复写成"修复了…的问题"，新能力写成
   "新增…（一句话说明用户能做什么）"。
3. **平铺成几个点**：连续编号列表，不用小标题分组，不写实现条件和
   过程状语（"仅当歌手支持时"这类，除非用户真的会在意）。
4. **术语用中文译名**：Bake = 固化（严禁"烧录"）、声线 = speaker、
   曲速 = tempo、拍号 = time signature、锚点 = anchor（可不译但要一致）。
5. 每条约一两句，句号结尾；用户读得懂，不出现代码/类名/功能名/引擎名。

## 步骤

1. 收集窗口内改动：`git log --since=<起点> --format="%s" main`（非 merge 提交）
   + 合并的 PR（`Merge PR #N:` 提交 + GitHub API 拉标题/描述）。
   注意窗口内直推 main 的提交（如 synthrt 更新）：属内部，通常不进日志。
2. 按规则 2 把每个改动转成用户视角的一句话；属内部的删掉。
3. 编号平铺输出；术语按规则 4。

## 用户认可范例

```
20260821-2325更新日志
1. 曲线固化笔刷：将模型生成的曲线转成手绘编辑层里可手动编辑的曲线。
2. 动画开关：设置里的动画等级改为简单的开关切换。
3. 在片段右边缘附近画音符、拖动、粘贴、缩放或量化时，片段自动向右延长，不再挡住编辑。
4. 音高与参数锚点编辑统一，Delete/Backspace/Esc 行为一致；孤点曲线不再被意外保留。
5. 修复了参数项禁用提示误报的问题。
6. 修复了跟随轨道和声线混合显示标签不同步的问题。
7. 修复了编辑区域焦点提示和快捷键响应对象异常的问题。
8. 修复了设置页滚轮误改数字控件数值的问题。
```

另一份见 `20260820-0042 更新日志`（字体切换/大小写连字符/参数提示/尖峰/歌词音节更新/粘贴优化）。
