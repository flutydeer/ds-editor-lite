# 四期：测试体系重构与跨平台 CI 实施计划

## 1. 目标与验收口径

按实际产品能力重组测试，补齐重要行为缺口，使完整 Editor、Connector 和测试可以在本地及三平台 CI 执行。实现依据为仓库代码，不补建早期路线中未落地的设计。

覆盖目标以 **Windows 完整环境中、约定测试边界内的业务逻辑行覆盖率达到 90%** 为参考，同时要求 Linux x64、Windows x64、macOS arm64 的规定 CI 集合通过。Linux 覆盖率独立报告，不合并平台或轮次命中，不将百分比设为机械的 CI 门槛。具体边界见[测试大纲](test-outline.md#10-业务逻辑覆盖统计边界)。

## 2. 设计原则

- 先按产品功能、关键工作流和失败风险划分职责，存量测试作为迁移素材。
- Qt Test 维护用例、断言、数据行和 Qt 输入。CTest 负责程序调度、环境、标签、超时、互斥及汇总。
- 新行为优先进入已有套件的 slot 或数据行，不按工具、功能提交或历史 bug 增加程序。
- 测试执行生产实现。替身只控制外部服务、设备、时间、进程和必要时序，不复制业务算法。
- 领域层验证规则，接口层验证转换和授权，进程层验证产品装配。GUI 必须经过真实控件事件并检查可见结果。
- 不复述工具 Schema，不约束工具总数，不维护工具清单镜像，不重复跨层业务矩阵，不建立像素或硬件组合矩阵。
- 有价值的失败回归归入所属行为。资源缺失、平台不适用、失败和通过分别记录。

## 3. 测试结构与公共设施

六类职责为基础数据与算法、编辑与应用状态、文档文件与异步工作流、自动化接口与 Connector、真实应用进程、界面组件与交互。内容及程序划分集中维护在[测试大纲](test-outline.md)，能力到源码的对应和旧入口去向集中维护在[覆盖矩阵](test-coverage-matrix.md)。

生产代码按依赖边界形成 EditorAutomationCore、EditorInferenceCore、EditorPreferencesCore、EditorGuiCore 和 EditorRuntime。产品及对应测试复用这些组件，消除用于重复编译生产代码的空 stub。完整应用夹具在程序内共用运行时，每例复位文档、历史、任务、配置及信号连接。

一个测试程序维护一个 Qt Test 类并执行一次 qExec。用例文件采用 `tst_<snake_case>.cpp`，多文件套件使用 test_main.cpp 和相应声明头。编译宏变体共用源码、独立构建。CTest 只注册程序，不另行同步函数清单。

公共设施提供完整 DSPX 内容快照、进程及数据根隔离、小型音频素材、受控线程池、文件写入故障和 GUI 输入。失败保留必要材料，成功释放自身资源。测试数据和插件目录注入仅在测试构建生效。

## 4. 跨平台与资源设计

| 环境 | 执行方式 |
|---|---|
| 通用逻辑和文件工作流 | 各支持平台均可本地执行，不能依赖 CI 环境变量 |
| 普通 GUI | offscreen。需要 Qt QDrag 的交互套件使用 minimal |
| 原生窗口及 RHI | 当前平台桌面，Linux CI 使用 Xvfb。实际图形后端按条件执行 |
| 模型集成 | 默认使用仓库自制的多语言、多声线微型声库，走正式加载、推理和导出路径 |
| 外部声库、GPU、音频设备和 MIDI 回环 | 按明确资源配置或能力探测执行，已配置资源执行失败不能降为跳过 |

微型声库不含真实训练权重或声库主体信息。GAME/RMVPE 实际模型、主观音质和跨驱动图像一致性保留本期边界。资源配置与跳过规则只在[执行计划](test-plan.md#3-运行条件)维护。

## 5. CI 建设与调试

workflow 对面向 main 的 PR 和 main push 触发，允许在 Draft PR 中调试。runner 使用 ubuntu-latest、windows-latest 和 macos-latest，架构分别为 x64、x64、arm64。

每个平台分开显示依赖、配置、完整构建、测试和产物收集。Linux 使用 coverage 构建，在测试之后用独立 Coverage 步骤生成报告。Windows/macOS 使用普通 Debug tests 构建，执行全部适用测试。工具链具体版本以 workflow 和依赖声明为准。

依赖缓存仅保存 Qt 和 vcpkg 包。键包含平台、工具链环境及依赖声明，每轮仍执行 vcpkg install，由 ABI 决定复用或重建。CMake 构建树不缓存。冷缓存、正常命中和依赖更新路径须经实际验证。

失败处理按环境与依赖、编译链接、运行时装配、行为断言、时限、隔离逐项定位首个根因。可本地复现时先验证失败用例及所属组，再完整验证、提交和推送新代码。新代码必须由新运行验证，不用旧 run 的重跑替代，不通过删除有效断言、沉默跳过或无依据扩大超时取得通过。

## 6. 实施顺序

| 阶段 | 交付与检查点 |
|---|---|
| 能力梳理 | 建立六类职责、覆盖矩阵、资源条件和文档基线 |
| 基础设施与 CI 引导 | 共用生产组件、统一入口与隔离设施，创建 Draft PR 并开始真实 CI |
| 领域和工作流 | 迁移基础、编辑、文档及异步测试，补齐重要缺口 |
| 接口、进程和 GUI | 验证公开接线、产品装配及真实输入，完成三平台适配 |
| 覆盖与产品修复 | 按未覆盖逻辑及行数选择补测，确认缺陷后修复，共享重复实现 |
| 验收与审查 | 本地完整测试及覆盖分析、三平台 CI、报告和 bot 审查闭环 |

每轮代码修改先完成 Windows 本地构建、规定测试及覆盖分析，再推送 CI。分析区分新增命中、生产代码重构和统计口径变化，不将减行数计作新增行为覆盖。实际完成情况见[实现报告](implementation-report.md)和[测试报告](test-report.md)。

## 7. 分支、提交与审查

使用独立 test-ci 分支和一个指向 main 的 PR。分层或相互独立的改动阶段提交，采用单行英文 Conventional Commits。代码注释使用英文，只解释最终实现需要的语义。阶段文档使用中文。

ready 前完成测试、CI 及报告。审查由仓库智能触发。真实问题修复并验证后，回复讨论并 resolve。受审代码的规定验证和 bot thumbs-up 或明确无问题结论同时成立，才完成交付。纯文档变更不要求重跑或重新等待已经验证的产品代码。
